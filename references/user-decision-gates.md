# 用户逐节点决策与确认基线

用于活动策划及涉及方案取舍的修订。默认由用户把控每个适用节点，AI负责把决策准备完整、落实已确认决定并跟踪可行性。这是项目控制，不要求用户用“陪练”口令。维护skill本身、只读审查、查询或计算不套活动审批链。

## 运行原则

当前节点：准备资料/核算/比较 → 提交决策卡 → 用户决定 → 登记确认基线 → 推进依赖该决定的下一节点。信息已经齐全也不能把AI推荐当成用户选择。

AI可自主做已授权范围内的检索、计算、交叉核验、风险检查和不依赖待决选择的准备。允许计算后续情景帮助当前决策，但标候选/假设，不将后续方案定稿、锁资源或写成已确认。不得只问空泛问题：先把可准备的内容做完，给出具体选项和影响后再请用户决定。

已有明确决定、持续有效的授权直接沿用，不重复索要确认。用户原话已指定目标、方案或边界时可作为相应节点的确认依据；记录能确认的范围，不能由一项选择推定后续全部批准。若当前节点在此前已明确确认且没有实质变化，简短回显已锁定内容后继续，无需为节点编号重新问一次。

## 各节点的决策对象

| 节点 | AI准备的决策材料 | 用户决定/确认基线 |
|---|---|---|
| 0 判局 | 活动与替代路径、需求提取、范围与约束 | 是否做、主目标、受众、预算/日期等边界及本次交付深度 |
| 1 研究 | 能改变方向的证据、冲突、未知及补研代价 | 采用哪些研究判断作为规划依据，是否补研或在明确假设下继续；确认不把假设变事实 |
| 2 行为 | 核心参与者收益、目标行为、冲突取舍 | 主次目标与成功判据，不能替用户调换业务目标 |
| 3 经营 | 预算选项、支付时点、资源边界、测量与降级 | 预算分配、资金/资源前提、可接受代价和必须保留项 |
| 4 表达 | 与目标匹配的表达主线或简明价值说明 | 主线/调性；无叙事需要时沿用已确认的简明表达范围，不强造故事 |
| 5 机制 | 有区别的候选、推荐理由、参与流程、资源风险与验证 | 选哪套核心机制、哪些保留或放弃、试验/预检的范围 |
| 6 执行传播 | 排期、岗位、容量、采购/票券/媒介、专业交接与备用方案 | 执行版本、服务承诺、资源配置与传播选择；实际预订/发布等另核已有外部授权 |
| 7 风险修复 | 已发现问题、修法成本、剩余风险与替代 | 修改、换方案、缩范围、延期或停止；用户接受风险不替代专业放行条件 |
| 8 成案 | 按确认基线整合的完整稿、差异表、未决项 | 哪一版为确认稿、尚需改哪些内容；未知仍在稿中明示 |
| 9 验收交接 | 完整性、一致性、资源/专业条件证据、未关闭项与接手人 | 接受交付或退回具体问题，确认后续执行边界；未核条件不能因接受交付被写成可执行 |

按真实任务取适用节点；节点不适用给理由，不能静默跳掉用户需要控制的取舍。同一轮可展示相邻节点的候选方便比较，但默认逐节点记录选择；明确同意合并确认时才按该范围合并。不得把“继续”“不错”跨越多个互不相关的待决问题解释为全案批准。

## 简短决策卡

每次只围绕当前节点：①本次决定什么；②选项与推荐依据（存在真实备选才列）；③预算/时间/资源/风险差别；④已核、假设与待核；⑤请用户选择或调整的具体项，以及影响哪些后续内容。默认一张小表或几个短段，详细计算入依据文件；不把已有信息再问一遍。

结尾明确“当前等待哪项决定、已锁定什么、尚未锁定什么”。若有多个决定，将真正相关项合并成少量问题；沉默、经过时间、AI自评或专业模拟均不算用户确认。

## 确认台账与变更

多轮项目在项目目录维护 `user-decisions.md`，也可使用同等字段的结构化记录；单轮任务保留在答复即可。不要写进skill安装目录。每项记录：decision_id、节点、决定内容/选项、条件与容许范围、所依据的输入/方案版本、用户原话及消息位置/日期、关联事实/模块/产物、状态、替代哪条旧决定。

状态：待决定 / 已确认 / 有条件确认 / 需重新确认 / 已撤回 / 已替代。只有明确对应用户决定才写已确认；有条件确认记录尚未满足的条件和期限，不伪装成条件已落实。用户明确授予AI一定范围的选择权时，记录授权原话、范围和期限；范围内的AI选择标“授权内决定”，不捏造成用户逐项选定。

用户确认值再登记project-state的facts（source回指decision_id和原话）；事实真伪、专业核验及外部动作回执另记。已确认预算上限不是供应商报价证据；技术audit通过不是用户批准。

目标、受众/人数、日期地点、预算总额或重要分配、核心机制、服务承诺、传播事实/授权、资源或专业条件发生变化时，先比较已确认范围：超出范围或改变关键可行性的，关联决定标需重新确认，关联产物按project-state标过期。交给用户“原决定→变化→影响→可选修法→推荐”，只暂停依赖该选择的定稿/承诺，其余工作继续。未受影响决定继续有效，不重启全流程。

用户直接明确提出新决定（如“预算上限改为8万”）即记录新上限，不再问同一上限；若必须因此删减承诺或换机制，准备影响分析，新增取舍仍由用户决定。错别字、同义表达、已授权范围内的排版等不重新确认；保存修订记录即可。旧确认历史保留，不覆盖成“始终如此”。

## 五入口的边界

- plan：默认按上述适用节点推进。“做完整策划”指最终交付完整，不代表把中途取舍都交给AI。
- quick：“直接给一版/先看全貌”允许一次给参考草案；未被明确选定的内容标候选/待决定，不写最终执行版。给草案不等于批准其全部节点。
- review：完整执行已授权的只读审查并交七段报告，不为了审查重复确认原案节点。原案写某个选择不自动证明用户已批准。进入改选方案时对新增取舍使用决策卡；用户已明确授权的具体修订直接落实。
- module：核预算、算容量、查资料等直接交结果。涉及在多个执行方案之间选定时，仅把该项取舍交用户；不扩成十步全案。
- retro：直接分析实际数据和承诺兑现；下一场的目标、预算或方案变更才形成新的待决项。

用户可明确授权指定范围的连续草拟或自主选择，也可随时收回；按自然语言实际含义执行，不设置固定口令，不要求重复授予已有权限。“按你推荐的A方案修改”已授权该具体修改；“输出简短”只改变表达长度，“开始吧”只启动当前已约定任务，不推定长期放弃节点控制。

## 三种验收不能混用

用户确认：选择方案与接受交付。质量验收：事实、数字、依赖、文档、交接是否完整。专业/执行确认：场地、供应商、专业负责人和外部操作的真实证据。三者分别记录，互不替代。老板模拟预演仍可选，不能替用户确认，也不能成为新的强制暂停环节。

当前脚本只校验已登记事实/依赖/文件及复核记录，不自动理解用户原话、判定确认范围或更新此台账。交付时人工/模型对照用户消息复查，并如实标明方法；不声称机器已验证审批真实性。
