# 固定交付协议

固定结构让读者可比较，不强制生成无关内容。未知、不适用、未检查必须显式标明，不能空表充数。用户指定格式优先。

## 节点决策卡与最终交付

活动策划按user-decision-gates.md先交当前节点的具体决定、备选/推荐、预算时间资源风险影响、已核与假设、待用户选择项。先完成准备再问，简短不等于跳过用户决策；当前节点已确认则直接沿用。决策卡不是最终方案，最终交付结构保持如下；用户明确要看全貌可提前交待确认参考草案。

## 篇幅与内部字段

用户说“一页/简短/直接给结果”时，正文默认600—900个可见字符（含表格文字，不计Markdown标记），最多一张表；只留目标、动作、资源、关键风险与下一步。存在额外必要细则时另放附件，不把所有潜在未知重复写三遍。普通用户正文不出现project_id、capability、input_revision等机器字段；它们留在项目状态或内部记录。对决策没有影响的工具限制不占正文。
完整审查保留七段，但默认先交一页摘要加问题表；问题很多再附明细，不把每个不适用模块展开成段。用户明确要详版时再展开。

## 完整策划：两份文件

1. `<项目>-活动方案.md`：决策摘要、目标与受众、机制与体验、适用传播、执行、预算、风险、验收、待确认。执行必需细则进入正文或附件。
2. `<项目>-决策依据.md`：范围与版本、事实/假设/来源、关键取舍、风险修法、检查结果与限制。不是内心独白或逐步思维。

方向草案用一页：目标、2—3个机制、推荐理由、资源假设、下一步。局部任务用：结论、依据、修改内容、验证状态、待确认。复盘用：目标与实际、数据质量、归因限制、失败原因、下一轮动作。

最终方案/依据回指用户确认版本，另列未决与有条件确认项；不因文件生成或验收通过写成用户已批准。完整项目交付前对照确认台账，明确本次请用户接受的版本与变化；已明确接受的范围不重复问。用户确认、质量验收和专业/执行证据分开呈现。

## 完整方案审查：固定七段

1. **结论**：可评审 / 修改后复审 / 当前版本阻断 / 证据不足；审查范围、原稿版本、置信度。
2. **保留项**：真正有效的内容；没有充分证据则如实写，不凑3条。
3. **问题与修法**：问题ID、原文页码/章节/表行、证据、严重度、影响、具体修法、责任人、复验条件。
4. **数字与链路核对**：预算、容量、时间、库存、权益、报名/传播/销售漏斗、数据口径；各为通过/失败/未知/不适用。
5. **信息与来源缺口**：已核、矛盾、过期、不可访问、需谁提供；不得把“未写”当“现实中没有”。
6. **修改前后差别**：原做法 → 建议做法 → 预期变化；未测收益标未验证。附按P0/P1/P2排序的行动。
7. **交付状态**：已查/未查、阻断项、下一动作；需要决策人预演时只加一个小节，不重复全套审查。

只审查则保存 `<项目>-审查报告.md`；审查并修订则另存修订稿、问题关闭表和变更摘要，保留原文。

## 状态不是批准

方向草案：有未核假设。可评审提案：可供决策，不代表可执行。执行条件已核对：在声明的时间和范围内资源/审批/预算/责任及阻断项已核验，不是执行结果。已执行结果：有实际回执或数据。审查结论“可评审”不得转换成老板已批准。

## 文件验收与聊天摘要

报告/文件请求落真实文件；Word/docx请求生成docx并保留源稿。依据文件只保留当前项目的来源、取舍与未核项，不复制其他案例的说明。确认非空、章节/数字一致、链接可用；正式排版检查表格溢出与分页，不能渲染时标明。工具不可用提供可读源稿，不声称已导出。
聊天默认：一句结论 + 最重要3项变化 + 实测/未测 + 文件路径。不得把模拟结果称为真实效果。

## 专业细则与版本记录

固定结构不增加固定表格数量。命中专业操作时，执行正文或附件给触发范围、实际核验方、放行依据、交接、异常停止/恢复与回执；提案级可列条件式待核。用户只要一页时，摘要保留当前最大阻断，其余现场必需细则进入附件。

修改前后表给可观察差异与复验结果，不用字数或专家数量证明提升。文件内容版本、需求覆盖、实际核验方法和未关闭承诺留在依据或状态记录；这些未查不标全局同步。会后承接明确接收人与期限，未关闭不写全部履约。
